Title:
End-to-end integration verification

Purpose:
Every preceding task validated with a build only. This is the single task that proves the system actually works together, and it is the only place the nine behavioral scenarios from the review are exercised against a running app. Several of the fixed bugs — the frozen scheduler, the leaked WebSocket, the data-destroying migration — are invisible in a unit test and only show up in a running container.

Dependencies:

Consumes:
Every artifact produced by every preceding task. This task changes no code.

Produces:
A verification report. No code artifact.

Files:
(none — this task must not modify any file)

Requirements:
Run the full suite, then the nine scenarios. Record the actual observed result for each, not an expectation.

1. `dotnet build` — must be 0 errors and 0 warnings.
2. `dotnet test` — must be 0 failures. Record the total test count and confirm it is non-zero; the pipeline previously matched no test project and reported a green no-op.
3. Bring the app up with `cd HopInLine && cp .env.example .env`, set `SA_PASSWORD`, then `docker compose up --build`. Confirm it is reachable at `http://localhost:8080`.

Then verify each scenario:

4. **Create and share.** Create a line with auto-advance at 1 minute and Auto Re-Add on. Confirm the creation page shows both a join link and a manage link, visibly distinguished.
5. **Position integrity.** Add three participants. Confirm the order is A, B, C, then advance several times and confirm positions stay distinct and **the same participant never comes up twice in a row**. This is the regression check for the two colliding numbering schemes.
6. **Pause.** Pause, then wait past the deadline. The line must **not** advance. Resume, and confirm the countdown continues from where it paused rather than jumping to a full interval. This is the regression check for the notification that restarted the timer.
7. **Restart resilience.** Start a countdown, then `docker compose restart web` mid-countdown. The line must resume advancing on schedule. This is the regression check for the missing `AddHostedService`.
8. **No browser at all.** With every browser tab closed, leave an auto-advancing line for two intervals, then reopen it and confirm it advanced while unobserved. The old scheduler only ran while a page was open.
9. **Access control.** Open the join link in a second browser. It must show live updates and the join box, and **no** management controls. The manage link must show them all. A manage URL with a wrong token must show none.
10. **Not found.** Open `/view-line/ZZZZZZZZ`. Expect a "line not found" message, not a crashed circuit or a blank page. Confirm `/list-lines` no longer exists.
11. **Long interval formatting.** Set the interval to 90 minutes. The countdown must read `1:30:00`, not `30:00`.
12. **No connection leak.** In browser dev tools, confirm exactly **one** WebSocket — the Blazor circuit — with no second connection to `/linehub`. Navigate in and out of a line ten times and confirm the count stays at one. Then leave an idle line open for a minute and confirm no per-second traffic: the countdown must tick with zero server round-trips.
13. **Data survives a migration.** With data in the database, add a trivial migration and redeploy. **The data must still be there.** This is the regression check for `EnsureDeleted()`.

Also confirm these review checks:
14. `git ls-files .vs` returns nothing, and no tracked file contains a password. Search the tracked set for `YourStrong!Passw0rd` and confirm zero hits.
15. `azure-pipelines.yml` triggers on `main` and requests SDK `10.x`.
16. The container runs as `app`, not `root` (`docker exec <id> whoami`).

- Do not use `EnsureDeleted`, drop the database, or reset the volume at any point. Scenario 13 depends on real persisted data.
- Do not commit anything.
