Title:
Add a shared duration formatter and tests proving intervals over an hour render correctly

Purpose:
`ViewLine.razor` formats remaining time with `ToString(@"mm\:ss")` in two places. That format specifier prints only the minutes **component** of a `TimeSpan`, so 90 minutes remaining renders as `30:00` and 24 hours renders as `00:00`. Both `StartLine` and `EditLine` allow intervals well past an hour, so this is reachable through the normal UI. JS-001 fixes the live countdown in JavaScript; this task provides the matching server-side formatter for the non-countdown labels and the tests that pin the behavior.

Dependencies:
TEST-001

Consumes:
TEST-001: the `HopInLine.Tests` project and its xunit setup

Produces:
`HopInLine.Data.Line.DurationFormat.Humanize(TimeSpan)` — consumed by VIEW-001 for its static duration labels.

Files:
- `HopInLine/Data/Line/DurationFormat.cs` (new)
- `HopInLine.Tests/DurationFormatTests.cs` (new)

Requirements:
1. Create `public static class DurationFormat` with one method:
   `public static string Humanize(TimeSpan value)`
2. Formatting rules. These match JS-001's `startCountdown` output character for character, so a server-rendered label and the live countdown beside it never disagree — with one deliberate exception, noted below, for non-positive spans.
   - zero and negative values format as `"0:00"`. This is the deliberate difference from JS-001, whose live countdown writes `"Auto-advance happening now..."` at or past the deadline. `Humanize` labels a configured interval, not a live deadline, so it has no "now" state.
   - under one hour: `m:ss` — minutes **not** zero-padded, seconds always two digits — so 90 seconds is `"1:30"`, and 9 minutes 5 seconds is `"9:05"`
   - one hour or more: `h:mm:ss` with minutes and seconds zero-padded — so 90 minutes is `"1:30:00"`
   - 24 hours or more: keep counting hours rather than rolling over — so 25 hours is `"25:00:00"`. Use `value.TotalHours`, floored, **not** `value.Hours`. `value.Hours` is the component and wraps at 24, which is the same class of bug being fixed.
   - seconds truncate toward zero, never round up
3. Implement it with explicit integer arithmetic on `TotalSeconds`, not with a `TimeSpan` custom format string. Format strings are exactly what caused the bug.
4. Create `DurationFormatTests.cs` with one `[Theory]` and `[InlineData]` rows covering, at minimum:
   | input | expected |
   |---|---|
   | `TimeSpan.Zero` | `"0:00"` |
   | 5 seconds | `"0:05"` |
   | 65 seconds | `"1:05"` |
   | 9m 5s | `"9:05"` |
   | 59m 59s | `"59:59"` |
   | 60 minutes | `"1:00:00"` |
   | 90 minutes | `"1:30:00"` |
   | 25 hours | `"25:00:00"` |
   | -30 seconds | `"0:00"` |
   Express the inputs as total seconds in the `InlineData` and build the `TimeSpan` inside the test, because `TimeSpan` is not a valid attribute argument type.
5. Add one plain `[Fact]` named `Humanize_DoesNotWrapAtTwentyFourHours` asserting that 25 hours does not format the same as 1 hour. This is the specific regression being locked down.

Constraints:
- Do NOT edit `ViewLine.razor`, `StartLine.razor`, or `EditLine.razor`. VIEW-001 adopts this formatter; the other two do not display durations this way. Editing them here would collide.
- Do NOT change the `max` attribute on any interval input; EDIT-001 and START-001 own those.
- Do NOT add a localization or culture parameter. Use `CultureInfo.InvariantCulture` for every conversion so the tests are stable on any machine.
- Do not use `TimeSpan.ToString` with any format string anywhere in `DurationFormat.cs`.
- Write no tests about pausing, advancing, positions, or authorization — other test tasks own those.

- 90 minutes formats as `"1:30:00"`, not `"30:00"`.
- Running the tests twice in a row gives identical results, and they pass under a non-invariant machine culture.
