Title:
Client-side countdown and confirm-dialog interop

Purpose:
`ViewLine.razor` currently runs a server-side `System.Timers.Timer` at 1-second intervals per viewer, calling `StateHasChanged` — a per-user, per-second re-render and diff over the Blazor circuit, forever (the timer is never stopped). Moving the countdown to the browser removes that traffic entirely. This task also provides the confirm helper that destructive actions need, since Delete Line / Remove / Delete Participant currently fire with no confirmation.

Dependencies:
(none)

Consumes:
(nothing)

Produces:
Browser interop contract consumed by VIEW-001 and EDIT-001:
- `window.hopInLine.startCountdown(elementId, targetUtcIso)` / `window.hopInLine.stopCountdown(elementId)`
- `window.hopInLine.confirm(message)` → `bool`

Files:
- `HopInLine/wwwroot/js/hopinline.js` (new)
- `HopInLine/Pages/_Layout.cshtml` (edit — add one `<script>` tag)

Requirements:
1. Create `wwwroot/js/hopinline.js` defining a single global `window.hopInLine` object.
2. `startCountdown(elementId, targetUtcIso)`:
   - Parse `targetUtcIso` as a UTC instant.
   - Immediately write the remaining time into `document.getElementById(elementId).textContent`, then update it once per second with `setInterval`.
   - Format, which must match `DurationFormat.Humanize` in FMT-001 character for character:
     - under one hour: `m:ss` — minutes **not** zero-padded, seconds always two digits. 90 seconds is `1:30`; 5 seconds is `0:05`; 59m59s is `59:59`.
     - one hour or more: `h:mm:ss` — minutes and seconds both zero-padded. 90 minutes is `1:30:00`.
     - past 24 hours, keep counting hours instead of wrapping: 25 hours is `25:00:00`. Compute hours as `Math.floor(totalSeconds / 3600)`, never with a modulo by 24. **The wrapping-component mistake is exactly the existing `ToString(@"mm\:ss")` bug, where 90 minutes renders as `30:00`.**
     - truncate seconds toward zero; never round up.
   - When remaining <= 0, write `"Auto-advance happening now..."` and clear the interval. This is the one place the two formatters deliberately differ: the static server-side `Humanize` renders a non-positive span as `0:00`, because it labels a configured interval rather than a live deadline.
   - Track intervals in a map keyed by `elementId`, and always clear any existing interval for that id before starting a new one, so repeated calls cannot leak timers.
   - If the element does not exist, do nothing and return without throwing.
3. `stopCountdown(elementId)`: clear and remove that id's interval. Safe to call for an unknown id.
4. `confirm(message)`: return the result of the browser's `window.confirm(message)`.
5. In `Pages/_Layout.cshtml`, add `<script src="js/hopinline.js"></script>` immediately BEFORE the existing `<script src="_framework/blazor.server.js"></script>` line.

Constraints:
- Plain ES5-compatible JavaScript. No modules, no imports, no build step, no external dependencies.
- Do not edit any `.razor` file. VIEW-001 and EDIT-001 wire these up.
- Do not remove or reorder the existing `blazor.server.js` script tag.
- All time maths is on UTC instants — never use the browser's local timezone for the target.

Acceptance Criteria:
- `window.hopInLine` exposes exactly `startCountdown`, `stopCountdown`, and `confirm`.
- A target 90 minutes in the future renders `1:30:00`; 90 seconds renders `1:30`; 5 seconds renders `0:05`; 25 hours renders `25:00:00`; a past target renders `Auto-advance happening now...`.
- Calling `startCountdown` twice for the same element leaves exactly one running interval.
- `startCountdown("does-not-exist", ...)` throws nothing.
- The script loads before `blazor.server.js` and produces no console errors on any page.

Validation:
`dotnet build` completes with 0 errors. Load the app and confirm `typeof window.hopInLine.startCountdown === "function"` in the browser console.

Handoff:
State the three exact JS function signatures and the element-id convention you expect callers to use.
